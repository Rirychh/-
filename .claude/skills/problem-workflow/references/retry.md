# 重試上限、換路規則、升級

## 為什麼要有上限

沒有上限的重試會變成無聲地燒時間：同一個問題改第九次，每次都差一點，
而且壞掉的任務一直卡在那裡，不會冒泡到人面前。

上限真正保護的不是成本，是**人的注意力**。人之所以願意把事情交出去，
是因為相信卡住的時候會被告知。這個信任一旦破掉，他下次就會自己盯著看——
整套分工就白做了。

## 上限：同一種改法，最多兩次

第二次還沒過，就不要再用同一種方式改。問題多半不在措辭或參數，
在**要求本身太難**，或是方法選錯了。

「同一種改法」指的是同一個維度上的微調。把溫度從 0.7 調到 0.6 再調到 0.5，
那是一次改法試了三回，不是三種改法。

## 換路是換維度，不是換措辭

換路的意思是**改變問題的形狀**，常見的三個方向：

### 一、縮小範圍

先做一個明確能成的小版本，確認路是通的，再往外長。

圖卡的「把圖上的字砍到剩主標」、程式的「先讓一個測試案例過」、
文章的「先寫完一節」都屬於這類。縮小之後若還是不行，那是方法問題，
不是份量問題——這個資訊本身就有價值。

### 二、降低精細度

放掉非核心的要求，保住主要目的。

圖卡的「拿掉背景道具、角色縮小」、報表的「先出月粒度不出日粒度」、
查詢的「先不管排序」。要明確記下放掉了什麼，交付時一併講。

### 三、換方法

同一個目的，換一條完全不同的路。

用程式判改成用人判、用 API 改成用 CLI、自己算改成找現成的、
生成改成模板填空。這條最有機會跳出死胡同，但也最該在前兩條之後才用，
因為成本最高。

## 不必跑滿預算就該直接升級的情況

預算是給「方法可能對、只是還沒調好」的情況。遇到下面幾種，
再試幾次也沒意義，立刻回報：

- **發現前提錯了**——需求建立在一個不成立的假設上
- **發現需求本身矛盾**——兩條要求無法同時滿足
- **要動到不該動的東西**——為了達標，得改掉使用者沒授權的範圍
- **缺關鍵資訊**——少一個只有人知道的東西，猜不出來也不該猜

這幾種情況硬試下去，最糟的結果不是失敗，是**湊出一個看起來成功的東西**。

## 升級的回報格式

回報的不是「做不到」，是**試過哪幾種、各差在哪**。人要做的決定是
「放寬哪條標準」或「改需求」，這個決定需要完整的失敗紀錄才做得出來。

```
這件事我試了 4 次，卡在〈哪一條標準〉：

1. 〈做法〉→ 〈結果，差在哪〉
2. 〈做法〉→ 〈結果，差在哪〉
3. 換路（縮小範圍）：〈做法〉→ 〈結果〉
4. 換路（降低精細度）：〈做法〉→ 〈結果，放掉了什麼〉

要你決定：〈兩到三個具體選項，不要開放式提問〉
```

最後一行很重要。「你覺得呢？」會把問題丟回去，人還得自己把選項想出來。
給具體選項，他只要挑一個。
