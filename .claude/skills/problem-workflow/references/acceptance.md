# 怎麼寫可逐條判斷的驗收標準

一條標準有沒有用，看一件事：**不認識這個任務的人，能不能拿著它判出過或退？**
判不出來的標準不是標準，是願望。

## 三問法

每寫一條，問自己三個問題。答不出任何一個，這條就要重寫：

1. **這條怎麼算退？** 答不出具體的退圖樣子，代表這條沒有邊界
2. **退的證據長什麼樣？** 要能指著某個地方說「就是這裡」
3. **誰判、用什麼判？** 是跑指令判，還是人看了判

## 模糊 vs 可判

| ✕ 判不出來 | ✓ 可逐條判 |
|---|---|
| 程式碼品質要好 | 新增的函式都有對應測試，`pytest` 全綠 |
| 文案要吸引人 | 標題 20 字內，開頭不用「在這個⋯⋯的時代」 |
| 圖要好看 | 角色三項特徵全對、文字無簡體、比例 4:5 |
| 回覆要專業 | 不出現「抱歉」以外的道歉語，每個數字都附出處 |
| 效能要改善 | 同一組輸入下，執行時間比改動前短，附兩次實測數字 |

左欄的共同問題是**把判斷權留給了做的人**。做的人總會覺得自己做的夠好——
這就是為什麼審的人不能是做的人，也是為什麼標準要在動手前寫。

## 每條標上誰判

寫完每條標準，在後面標記判定方式：

- **[程式]** — 能用指令、腳本、測試判的。**標了就要真的寫出來**，
  不要標了之後還是用眼睛看。程式判的好處不是快，是它不會因為你累了就放水
- **[人眼]** — 程式判不了的（讀起來順不順、角色像不像、語氣對不對）

一份標準裡如果一條 [程式] 都沒有，通常不是任務特殊，是還沒想清楚
哪些東西其實可以被機械檢查。反過來，全部都是 [程式] 也可疑——
多半漏掉了真正重要但難量化的那條。

## 數量：三到七條

少於三條，通常是漏了東西（最常漏的是「格式／規格」那類無聊但會致命的）。
多於七條，條目會開始互相重疊，判定時變成重複勞動，而且每條的份量被稀釋，
退圖時講不清楚到底卡在哪。

## 動手之前寫

這點最容易被跳過，但跳過了整套就失效了。

**事後才寫的標準，會被已經做出來的東西反向定義。** 你會不自覺地把標準
寫成剛好符合手上這個成果的樣子——那不是驗收，是替成果找理由。
先寫標準，等於先承諾什麼算完成，之後就只是比對，不是重新談判。

## 標準本身也會錯

跑了幾輪之後，如果某條標準反覆擋下明明沒問題的成果，那是標準寫錯了，
不是成果不行。這時候該改標準——但要**明講你在改標準、為什麼改**，
而不是這一次偷偷放水。放水不會留下紀錄，改標準會。
