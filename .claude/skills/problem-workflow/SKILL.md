# 解決問題的工作流

這套模式要處理的是一種具體的浪費：**事情做完了，但不知道算不算完成**，
於是來回確認、重做、再確認，時間花在溝通而不是在做事。

解法不是更努力，是把三件事定下來：**誰判、照什麼判、什麼時候該停下來找人**。

這份文件是通用版。`references/example-image-card.md` 是把它套在產圖卡上的
完整實例，看不出怎麼落地時先看那份。

## 三個角色

| 角色 | 負責 | 不負責 |
|------|------|--------|
| 出需求的 | 講要什麼、給誰、什麼算完成；驗收成品 | 決定怎麼做、看每一版草稿 |
| 做的 | 照規格做 | 判斷自己做得夠不夠好 |
| 審的 | 照明文標準逐條判過／退 | 動手改 |

**一個人同時兼做跟審的時候，要在時間上分開**：做完先停，換上審的身分，
拿著寫好的標準逐條比對。做的人總覺得自己做得夠好——這不是態度問題，
是視角問題，而且對人跟對模型都一樣。這就是為什麼標準必須在動手前寫完。

---

## 五個步驟

### 一、收需求

問清楚三件事：**要什麼、給誰或用在哪、什麼算完成**。

缺的一次問完，不要一題一題來回。「什麼算完成」最常被跳過，但它決定了
後面所有事——對方講不出來也沒關係，你寫成草案給他確認，比憑空猜好。

其他細節（怎麼做、用什麼工具、分幾步）不要問，那是你的工作。

### 二、補規格

把對方沒講但必須定的事補滿。最常漏的是這幾類：
**格式、尺寸或份量、語言與語氣、不能動的範圍、交付形式**。

如果有**每次都該一樣的東西**（一組固定設定、一份術語表、一個角色的長相、
一份 API 合約），把它固定寫下來，之後每一輪**逐字複製**貼過去。
每次重寫就等於每次重新擲骰——這是重做的一大來源，而且很難事後查出來。

`assets/task-card.md` 是一張可以直接複製去填的任務卡。

### 三、動手之前，先寫驗收標準

三到七條，每條都要能被不認識這個任務的人判出過或退，
而且每條標記 **[程式]** 或 **[人眼]**。

**標了 [程式] 就要真的寫出來。** 寫成腳本的好處不是快，是它不會因為
你今天趕時間就放水；而且常常能順便擋掉連看都不必看的情況。

為什麼一定要在動手前寫：**事後寫的標準會被已經做出來的東西反向定義**，
你會不自覺地把標準寫成剛好符合手上成果的樣子。那不是驗收，是替成果找理由。

寫法、反例對照與三問法在 `references/acceptance.md`。

### 四、做

照規格做。做完**不要自己宣告過關**，交給下一步。

### 五、審

逐條判定，逐條寫下來，不要只給一句「可以了」。寫下來有兩個作用：
退件時能明確講出卡在哪，才改得動；過了時能讓人回頭檢查你是不是真的每條都看了。

**全過才算過。任一條沒過就是退。** 沒有「過五條算不錯」——
一旦開始通融，標準會一路鬆到跟沒有一樣，而且是人要花時間重看每一件。

沒過就回到第四步，**針對沒過的那條改**。重試有上限，見下。

## 重試上限

**同一種改法，最多兩次。** 第二次還沒過，問題多半不在措辭或參數，
在要求本身太難或方法選錯了。改走換路——換路是**換維度，不是換措辭**：

1. **縮小範圍**——先做一個明確能成的小版本
2. **降低精細度**——放掉非核心要求，保住主要目的，並記下放掉了什麼
3. **換方法**——同一個目的，換一條完全不同的路

兩條換路都走完才找人，而且回報的不是「做不到」，是**試過哪幾種、各差在哪**，
最後附兩到三個具體選項讓對方挑，不要開放式提問。

遇到**前提錯了、需求本身矛盾、要動到沒被授權的範圍、缺只有人知道的關鍵資訊**，
不必跑滿預算，立刻回報——硬試下去最糟的結果不是失敗，
是**湊出一個看起來成功的東西**。

完整的換路說明與回報格式在 `references/retry.md`。

## 什麼時候不要用這套

這套有固定成本：寫規格、寫標準、記判定。值不值得看任務。

**不要用在**：單純的問答、查一個事實、一兩步就做完的小事、
使用者正在旁邊逐步盯著一起做的時候。那些情況直接做比較快，
硬套流程只是在製造儀式感。

**值得用在**：交付物會被別人拿去用、同一類事情之後還會再做、
已經重做過一次以上、或使用者明確說「我只看結果」。

判斷基準很簡單：**如果這件事做錯了，發現得晚不晚、重做貴不貴。**
兩個都「不」的話，直接做。
